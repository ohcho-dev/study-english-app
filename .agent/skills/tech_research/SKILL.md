# Tech Research & Learning Material

외부 기술을 조사하여 학습 자료(가이드 문서)를 작성하라는 요청을 받았을 때, 이 스킬의 지침을 따릅니다.

> **목적**: 해당 기술의 전체 그림을 파악하고, 우리 서비스에 최적의 선택을 도출하는 실용적 학습 자료를 만드는 것

---

## 1. 조사 프로세스

**반드시 이 순서**로 진행합니다. 순서를 건너뛰지 않습니다.

### 1단계: 내부 코드 분석 (Inside-Out)

외부 문서를 보기 **전에** 우리 코드를 먼저 분석합니다:

- 해당 기술을 사용하는 **서비스 파일** 전체 스캔
- **의존 패키지/SDK** 확인 (버전 포함)
- **설정값/하드코딩** 수집 (모델명, 엔드포인트, 파라미터 등)
- **호출 흐름** 추적 (어디서 호출되고, 결과가 어디로 가는지)
- **코드 주석/TODO** 수집 (과거 의사결정 흔적)

> **왜 먼저?**: 외부 문서의 정보를 "우리 코드와 맞는가?"로 검증하는 기준선이 됩니다. 외부 문서만 보면 이론과 실제의 불일치를 놓칩니다.

### 2단계: 공식 문서 조사 (Outside-In)

제공사의 **공식 문서**를 중심으로 조사합니다:

- **제품 구조**: 전체 라인업, 모델/티어/등급 분류
- **가격 정책**: 과금 단위, 무료 할당량, 등급별 가격
- **제한 사항**: 할당량(QPM), 리전 제한, 데이터 제한 등
- **API 사양**: 파라미터, 설정 옵션, 입출력 형식
- **출시 상태**: GA / 프리뷰 / 디프리케이션

> **원칙**: 가격, 할당량, 출시 상태 같은 팩트는 **반드시 공식 문서에서 검증**합니다. 블로그나 커뮤니티 글은 이해를 돕는 참고 자료로만 활용합니다.

### 3단계: 교차 검증 (Cross-Check)

1단계(코드)와 2단계(문서)의 **불일치**를 찾습니다:

- 코드의 하드코딩 값이 최신 사양과 맞는가?
- 코드 주석에 적힌 정보가 여전히 유효한가?
- 우리 배포 환경(리전, 인증)에서 사용 가능한가?
- 더 나은 옵션이 출시되었으나 코드가 반영하지 못한 것이 있는가?

> 불일치 발견 시: 문서에 `⚠️` 표시 + 코드 수정 필요 여부 기록

### 4단계: 대안 비교 (Alternatives)

같은 문제를 해결하는 **다른 접근법**과 비교합니다:

- 타사 서비스 (같은 기능, 다른 제공자)
- 같은 제공사 내 대체 API (개별 API vs 통합 API 등)
- 오픈소스 / 자체 구현 가능성

## 2. 평가 지표 프레임워크

### 7대 기본 지표

기술 선택 시 **항상** 평가하는 지표입니다. 기술 분야에 관계없이 공통 적용됩니다:

| # | 지표 | 질문 | 측정 방법 |
|---|------|------|----------|
| 1 | **비용 (Cost)** | 월/연 얼마인가? | 공식 가격 × 예상 사용량 시뮬레이션 |
| 2 | **성능 (Performance)** | 속도, 처리량, 응답 시간은? | 실측 또는 공식 벤치마크 |
| 3 | **품질 (Quality)** | 출력이 얼마나 정확/우수한가? | 공식 벤치마크 또는 주관 평가 |
| 4 | **안정성 (Reliability)** | GA인가? SLA는? 장애 빈도는? | 출시 상태 + SLA 문서 |
| 5 | **확장성 (Scalability)** | 사용량 증가에 대응 가능한가? | 할당량, 동시 요청 수, 상위 티어 존재 |
| 6 | **통합성 (Integration)** | 기존 시스템에 쉽게 붙는가? | SDK 호환, 인증, 배포 환경 정합성 |
| 7 | **복잡도 (Complexity)** | 도입/유지에 얼마나 드는가? | 코드 변경량, 신규 의존성, 학습 곡선 |

### 서비스 특화 지표

7대 지표 외에 **해당 프로젝트의 핵심 요구사항**에서 파생되는 지표를 추가합니다.

도출 방법:
1. "이 기술을 왜 도입하는가?" → 핵심 목적에서 지표 도출
2. "우리 서비스의 차별점은?" → 차별 요소에서 지표 도출
3. "사용자가 가장 민감하게 느끼는 것은?" → UX 우선순위에서 지표 도출

### 가중합 점수 계산

```
1. 지표 선정 → 7대 기본 + 서비스 특화
2. 가중치 배분 → 합계 100%
   - 핵심 목적 관련: 15~20%
   - 사용자 체감:    10~15%
   - 운영/비용:      5~10%
   - 기술 요소:      5%
3. 각 옵션별 5점 만점 채점
4. 가중합 = Σ (점수 × 가중치)
5. 순위 도출 + 근거 설명
```

```

```

### 문서 섹션 (순서대로)

| # | 섹션 | 내용 | 필수 |
|---|------|------|------|
| 1 | **기술 용어 사전** | 핵심 용어를 초보자 눈높이로 설명 | ✅ |
| 2 | **핵심 개념 / 시스템 구조** | 전체 구조, 제품 분류, 동작 원리 | ✅ |
| 3 | **옵션별 상세 비교** | 각 모델/티어의 기능·품질·가격 | ✅ |
| 4 | **가격 분석 + 비용 시뮬레이션** | 과금 체계 + 현실적 사용량 기준 월 비용 | ✅ |
| 5 | **설정/파라미터 가이드** | 모든 설정값 (범위, 기본값, 우리 서비스 값) | ✅ |
| 6 | **API / 통신 방식** | SDK 사용법, 호출 경로, 프로토콜 | ✅ |
| 7 | **운영 환경 호환성** | 리전, 인증, 배포 환경과의 정합성 | ✅ |
| 8 | **경쟁/대안 비교** | 타사 서비스 또는 대체 접근법 | ✅ |
| 9 | **현재 구성 (AS-IS)** | 코드 분석 기반 현재 상태 | ✅ |
| 10 | **지표 기반 분석** | 가중합 점수 평가 + 순위 + 추천 | ✅ |
| 11 | **고도화 로드맵** | 난이도순 단계별 개선 방안 | ✅ |
| 12 | **참고 문서 링크** | 공식 문서 URL | ✅ |

> 기술 특성에 따라 섹션을 합치거나 세분화할 수 있으나, 위 항목은 빠트리지 않습니다.

## 4. 비용 시뮬레이션 기준

### 가정 설정

조사 대상 기술의 사용 패턴을 다음 형식으로 정의합니다:

```
사용자 수:       일 [N]명
사용자당 동작:   [M]회/세션
동작당 데이터:   [크기 또는 길이]
서비스 특화 변수: [해당 시 추가]
기간:            월 30일 기준
```

### 계산 순서

1. **월간 총 사용량** 산출
2. **무료 할당량** 차감 (해당 시)
3. **옵션별 월 비용** 비교표 작성
4. **파이프라인 합산** (여러 API 결합 시 전체 비용)
5. **스케일 시나리오** (사용자 10배, 100배 증가 시)

## 5. 작성 원칙

| 원칙 | 설명 |
|------|------|
| **정확성** | 가격·할당량·출시 상태는 공식 문서에서 검증. 검증일 명시. 확인 불가 시 `⚠️ 확인 필요` 표기 (TBD 금지) |
| **학습자 관점** | 비유와 다이어그램으로 설명. 용어 첫 등장 시 용어 사전 참조. 코드의 실제 사용례를 함께 보여줌 |
| **의사결정 지원** | 장단점 나열에 그치지 않고 **가중합 점수 → 순위 → 추천 → 근거** 도출. "다음에 무엇을 할까"의 로드맵 제시 |
| **유지보수성** | 문서 상단에 작성일·대상·목적 기재. 가격 정보에 검증일 명시. 링크는 문서 맨 끝에 정리 |
