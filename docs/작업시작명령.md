## 2단계: 현재 구현된 기능 파악

### 2-1. 핵심 기능 — Conversation (대화 시나리오)

현재 서비스의 핵심은 **AI 대화 시나리오** 기능입니다. 두 가지 모드가 있습니다:

#### Latency Lab (Run0) — 레이턴시 측정용
- **Server**: `app/services/conversation/run0_service.py` — 1회성 STT→LLM→TTS 파이프라인
- **Admin**: `(fsd)/features/conversations/model/useRun0.ts`, `ui/Run0Runner.tsx`

#### My Turn (시나리오) — 다자간 대화 시뮬레이션 (현재 개선 대상)
- **Server**: `app/services/conversation/my_turn_service.py` — 멀티턴 대화 관리
- **Server**: `app/services/conversation/scenario_director.py` — 시나리오 디렉터 (턴 관리)
- **Admin**: `(fsd)/features/conversations/model/useMyTurn.ts`, `ui/MyTurnRunner.tsx`
- **기획 문서**: `docs/plan/my-turn-master-plan.md`, `docs/plan/my-turn-conversation-spec.md`

#### 공통 서비스
| 파일 | 설명 |
|------|------|
| `app/models/conversation.py` | 대화 관련 DB 모델 (Template, Session, Turn 등) |
| `app/schemas/conversation.py` | Pydantic 스키마 |
| `app/services/conversation/stt_service.py` | Google Cloud STT |
| `app/services/conversation/tts_service.py` | Google Cloud TTS |
| `app/services/conversation/gemini_tts_service.py` | Gemini TTS |
| `app/services/conversation/template_service.py` | 템플릿 CRUD |
| `app/api/v1/conversations.py` | 대화 관련 API 엔드포인트 |

### 2-2. 접근 제어 시스템 (최근 구현)

역할 기반 접근 제어(RBAC)가 구현되어 있으며, `admin`과 `tester` 두 역할이 있습니다:

#### Server
| 파일 | 설명 |
|------|------|
| `app/models/account.py` | Account, PagePermission 모델 |
| `app/services/auth_service.py` | 인증, JWT, 계정/권한 CRUD (bcrypt 직접 사용) |
| `app/api/v1/auth.py` | 로그인(/login), 사용자 정보(/me) API |
| `app/api/v1/admin.py` | 계정/권한/템플릿 공개 관리 API (admin 전용) |
| `app/api/deps.py` | CurrentAccount, AdminAccount 의존성 |
| `scripts/init_access_control.py` | DB 초기화 스크립트 (배포 시 Dockerfile CMD에서 자동 실행) |

#### Admin
| 파일 | 설명 |
|------|------|
| `(fsd)/shared/lib/auth.ts` | 토큰 관리, login/logout, fetchMe |
| `(fsd)/shared/lib/api.ts` | API 클라이언트 (Authorization 헤더 자동 포함) |
| `(fsd)/shared/providers/AuthProvider.tsx` | 인증 상태 관리, 비인가 리다이렉트, 역할 기반 경로 차단 |
| `(fsd)/widgets/sidebar/ui/AppSidebar.tsx` | 역할별 메뉴 필터링, 로그아웃 버튼 |
| `app/login/page.tsx` | 로그인 페이지 |
| `app/(dashboard)/settings/access-control/page.tsx` | 접근 제어 설정 (계정/권한/템플릿 관리, 비밀번호 변경) |

#### 주요 동작
- **admin 역할**: 모든 페이지 접근 가능, 계정/권한/템플릿 관리 가능
- **tester 역할**: 허용된 페이지만 접근 가능, URL 직접 입력도 차단
- **템플릿 필터링**: tester는 `is_public_to_tester = true`인 템플릿만 표시
- **JWT**: `sub`(account id) + `role` + `username` 포함, localStorage에 저장

## 4단계: 기존 코드 분석

다음 코드를 분석하여 현재 구현 상태를 파악하세요:

### Server (apps/server/)
```
app/models/conversation.py          ← DB 모델 (Template, Participant, Session, Turn 등)
app/schemas/conversation.py         ← Pydantic 스키마
app/services/conversation/          ← 모든 대화 관련 서비스
app/api/v1/conversations.py         ← API 엔드포인트

app/services/auth_service.py        ← 인증 서비스
app/api/deps.py                     ← CurrentAccount, AdminAccount 의존성
```

### Admin (apps/admin/)
```
src/(fsd)/features/conversations/   ← 대화 관련 Feature 모듈 전체
  model/useRun0.ts                  ← Latency Lab 훅 (재사용 가능한 패턴 참고)
  model/useMyTurn.ts                ← My Turn 훅
  ui/Run0Runner.tsx                 ← Latency Lab UI (재사용 가능한 컴포넌트 참고)

  api/conversationsApi.ts           ← 대화 API 클라이언트
src/(fsd)/shared/providers/AuthProvider.tsx ← 인증/역할 관리
src/(fsd)/shared/lib/auth.ts        ← 인증 유틸리티
src/(fsd)/shared/config/constants.ts ← 라우트 상수
```

## 5단계: 개발 시 필수 유의사항

1. **접근 제어 고려**: 새 페이지 추가 시 `scripts/init_access_control.py`의 `PAGE_SEEDS`에도 추가 필요. AuthProvider의 역할별 분기 로직도 고려할 것.
2. **역할별 UI 분기**: `useAuth()` 훅으로 `user.role`을 확인하여 admin/tester별 UI를 분기할 것.
3. **API 인증**: 인증이 필요한 새 API는 `CurrentAccount` 또는 `AdminAccount` 의존성을 사용할 것.
4. **FSD 아키텍처**: Admin은 Feature-Sliced Design 아키텍처를 따름. 새 모듈 생성 시 `.agent/skills/scaffold_fsd_module/SKILL.md` 참고.
5. **기존 기능 보호**: Latency Lab(Run0) 페이지와 기존 기능에 영향을 주지 않도록 주의.
6. **DB 마이그레이션**: 스키마 변경 시 Alembic 마이그레이션 파일을 생성하고, 터미널 명령어 실행을 클라이언트에게 요청할 것.
7. **배포 환경**: Server는 GCP Cloud Run + Cloud SQL(PostgreSQL), Admin은 Cloud Run. Dockerfile에서 `alembic upgrade head` → `init_access_control.py` → `uvicorn` 순서로 실행됨.
8. **코드 컨벤션 준수**: `.gemini/rules/`의 코딩 규칙을 반드시 따를 것.

## 6단계: 이번 업무 — [My Turn(시나리오)] 화면 개선

### 6-1. UI/UX 전략 및 모바일 대응
- 현재 단순 채팅창 형태인 세션 대화 우측 인터페이스를 **서비스 특성에 맞게 재설계** 필요
- **모바일 대응 필수** — admin 계정, tester(일반) 계정 모두 반영
- 앞으로 추가될 다양한 기능과 모바일 이용을 **예상하여 확장 가능하게 설계**

### 6-2. STT/LLM/TTS 모델 선택 기능
- 템플릿 설정 후 각 참여자별 STT/LLM/TTS 모델 선택 기능 검토 및 보완
- **Latency Lab(Run0) 페이지의 유지보수 용이한 훅/컴포넌트를 재사용**하도록 코드 변경 (`useRun0.ts`, `Run0Runner.tsx` 패턴 참고)
- **일반계정(tester)**: STT/LLM/TTS 모델 선택 UI 제거 → 발화 속도와 난이도만 설정 가능
- **관리자계정(admin)**: My Turn 화면에서 특정 템플릿의 각 발화자별 모델 값 저장 가능
  - 관리자가 저장한 모델 값은 서버에 영구 저장되어 일반계정에도 동일하게 적용
  - 일반계정에서 변경한 발화 속도/난이도는 **세션 시작 시에만 적용**, 서버 저장 없음
  - 관리자가 저장한 발화 속도/난이도는 일반계정의 **기본값(default)**으로 표시

### 6-3. 핸즈프리 기능
- 사용자 발화 턴 시 **핸즈프리로 녹음 자동 시작** — 내 차례임을 명확히 인지시킬 UI 필요
- 녹음 중 **명확한 발화가 없거나 잡음만 감지**되는 경우의 처리 전략 설계
- 핸즈프리로 인한 사용성 저하 방지 전략 필요
- **녹음 일시정지 기능** — "생각할 시간이 필요하면 일시정지를 누르세요" 유도 포함
  - 일시정지 버튼 클릭 수, 시간 등은 기록 (추후 학습 리포트용)

### 6-4. 무음 환경 모드
- 소리를 낼 수 없는 환경을 위한 **텍스트 입력 모드**
- 기존 STT→LLM→TTS 프로세스와 다른 프로세스로 인지되어야 함

### 6-5. STT/LLM/TTS 파이프라인 개선
- STT에서 **사용자 음성 데이터 분석** (톤, 감정 등)
- 분석 결과를 LLM으로 전달 → LLM이 TTS 프롬프트에 톤/감정 반영
- 직전 발화의 감정 맥락을 이어가는 자연스러운 대화 구현

### 6-6. 오케스트레이션 LLM 기능 개선
- 턴 선택 과정에서 **사용자 발화 의도를 분석**하여, 특정 참여자에게 말을 건 것으로 판단되면 해당 참여자에게 발화 턴을 넘겨야 함
- 현재 `scenario_director.py`의 턴 배분 로직을 개선하여, 사용자 발화 내용/맥락 기반의 **지능적 턴 할당** 구현 필요
