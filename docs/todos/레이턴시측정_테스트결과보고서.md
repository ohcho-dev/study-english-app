## 1. 측정 기준 변경 사항

### 1.1 새로운 타임스탬프: t1.5 (LLM POST 도착)

기존에는 STT 완료(t1)부터 LLM 완료(t2)까지를 하나의 "LLM 레이턴시"로 측정했으나, 이번 변경으로 **네트워크 왕복 시간(Transit)**과 **순수 LLM 처리 시간**을 분리 측정한다.

| 타임스탬프 | 설명 | 클럭 위치 |
|-----------|------|----------|
| t0 | 사용자 녹음 종료 | Client |
| **t1** | STT is_final 수신 | Server (gRPC/동기) |
| **t1.5** | LLM POST 요청 서버 도착 | Server (HTTP) |
| t2 | LLM 응답 완료 | Server |
| t2.5 | TTS 완료 | Server |
| t3 | 오디오 재생 시작 | Client |

### 1.2 측정 구간 정의

```
E2E = t3 - t0 (사용자 체감 전체 지연)

STT     = t1 - t0   (음성→텍스트 변환)
Transit = t1.5 - t1  (STT 완료 → LLM 요청 도착, 네트워크 왕복)
LLM     = t2 - t1.5  (순수 LLM 처리)
TTS     = t2.5 - t2  (텍스트→음성 변환)
Client  = t3 - t2.5  (오디오 다운로드 + 재생 준비)
```

### 1.3 동기식 vs 스트리밍식 차이

| 항목 | 동기식 (Sync) | 스트리밍식 (Streaming) |
|------|-------------|---------------------|
| STT 방식 | 서버에서 동기 STT API 호출 | WebSocket으로 실시간 스트리밍 |
| t1 위치 | 서버 동기 STT 완료 시점 | 서버 gRPC is_final 수신 시점 |
| t1.5 | t1과 동일 (같은 요청 내 처리) | 클라이언트→서버 HTTP POST 도착 시점 |
| **Transit** | **항상 0ms** | **네트워크 왕복 시간 발생** |

## 3. 핵심 분석

### 3.1 동기식 vs 스트리밍 E2E 비교 (Latency Lab 기준)

```
동기식:     ████████████████████████████████████████████████▏ 4.65s
스트리밍:   ███████████████████████████████████▎              3.53s
                                                          (24% 감소)
```

**스트리밍의 E2E 감소 원인:**
- STT가 3.11s → 1.44s로 감소 (지속적으로 음성을 서버에 전송하므로 is_final까지 빠름)
- Transit 436ms가 추가되지만, STT 절감(1.67s)이 훨씬 큼
- **결론: 스트리밍이 E2E 관점에서 확실히 유리**

### 3.2 Transit 발생 원인 및 경로 분석

#### Latency Lab 스트리밍 (~436ms)

```
서버 is_final 생성 ─┐
                    ├─ WebSocket 메시지 전송 (~50ms)
클라이언트 수신     ─┤
                    ├─ isDone 대기 + React 상태 업데이트 (~100ms)
processStreamingResult 호출 ─┤
                    ├─ HTTP POST 전송 (~50ms)
서버 POST 도착      ─┘
                    총 약 ~400ms
```

#### My Turn 스트리밍 (~2,130ms)

```
서버 is_final 생성 ─┐
                    ├─ WebSocket 메시지 전송 (~50ms)
클라이언트 수신     ─┤
                    ├─ isDone 대기 (~500ms~1s, STT 세션 정리 포함)
                    ├─ useEffect 트리거 대기 (~50ms)
                    ├─ UI 상태 업데이트 (streamingText, streamingIsFinal) (~100ms)
sendText 호출       ─┤
                    ├─ HTTP POST 전송 (~50ms)
                    ├─ 서버 process_user_turn 진입 (~50ms)
서버 t1.5 기록      ─┘
                    총 약 ~2,100ms
```

**My Turn이 더 느린 이유:**
1. **`isDone` 대기**: `is_final` 후 별도의 `done` 메시지를 기다림 (STT 세션 정리 시간 포함)
2. **UI 업데이트 오버헤드**: 스트리밍 텍스트 표시, 상태 전환 등 추가 렌더링
3. **서비스 레이어 차이**: `process_user_turn`이 `process_text`보다 더 많은 전처리 수행

## 4. 아키텍처 개선 검토

### 4.1 현재 아키텍처 (클라이언트 중계 방식)

```
┌──────────┐     WebSocket      ┌──────────┐     gRPC      ┌──────────┐
│  Client  │◄──────────────────►│  Server  │◄─────────────►│ STT API  │
│          │                    │          │               │ (Google) │
│          │     HTTP POST      │          │               └──────────┘
│          │───────────────────►│          │
│          │◄───────────────────│  LLM→TTS │
│          │     Response       │          │
└──────────┘                    └──────────┘
     ▲                               ▲
     │      Transit = 이 구간        │
     └───────────────────────────────┘
```

### 4.2 대안: 서버 내부 처리 방식

```
┌──────────┐     WebSocket      ┌──────────────────────────┐
│  Client  │◄──────────────────►│  Server                  │
│          │                    │  ┌─────┐ ┌───┐ ┌───┐    │
│          │  audio chunks ───► │  │ STT │→│LLM│→│TTS│    │
│          │  ◄── final+reply   │  └─────┘ └───┘ └───┘    │
└──────────┘                    └──────────────────────────┘
                                      Transit ≈ 0ms
```

### 4.3 장단점 비교

| 항목 | 현재 (클라이언트 중계) | 대안 (서버 내부 처리) |
|------|---------------------|---------------------|
| **Transit** | 436ms~2.1s | **≈ 0ms** |
| **E2E 절감** | - | **약 400ms~2s 절감** |
| **서버 리소스** | WebSocket 짧게 유지 | WebSocket 장시간 점유 (STT+LLM+TTS) |
| **동시접속** | 높음 | **낮아질 수 있음** (커넥션당 처리 시간 증가) |
| **Cloud Run 호환** | 좋음 | **타임아웃 주의** (기본 300s) |
| **에러 처리** | HTTP 재시도 간단 | **WebSocket 내 복구 복잡** |
| **코드 구조** | STT/LLM 분리 (깔끔) | **결합도 증가** |
| **TTS 오디오** | URL 반환 (효율적) | **바이너리 전송 필요** |
| **Latency Lab 재사용** | 동일 파이프라인 공유 | **별도 구현 필요** |
| **배포/스케일링** | 독립적 | **함께 스케일링** |

### 4.4 권장 방향: 현재 구조 유지 + Transit 최적화

서버 내부 처리 방식은 Transit을 0으로 만들 수 있지만, **아키텍처 복잡도 증가와 Cloud Run 환경의 제약**을 고려하면 현재 구조를 유지하면서 Transit을 최소화하는 것이 안전하다.

#### 즉시 적용 가능한 최적화:

1. **`is_final` 즉시 POST 전송** (현재 `isDone` 대기 제거)
   - 예상 효과: My Turn Transit 2.13s → ~400ms 수준
   - 리스크: 낮음 (done 메시지는 정리용이므로 LLM 호출에 불필요)

2. **React 상태 업데이트 비동기화**
   - `sendText` 호출을 UI 업데이트보다 먼저 실행
   - 예상 효과: ~100ms 추가 절감

3. **서버 측 `process_user_turn` 진입점 최적화**
   - FormData 파싱 전에 즉시 `t1_5_llm_start` 기록
   - 예상 효과: ~50ms 절감

#### 중장기 검토 사항:

- 서버 내부 처리 방식 도입 시 **LLM 스트리밍 응답 + TTS 청크 전송** 구현 필요
- WebSocket 기반 양방향 스트리밍으로 전환 시 E2E를 **2s 이하**로 줄일 가능성 있음
- 단, Cloud Functions / Cloud Run의 WebSocket 유지 비용과 타임아웃 정책 사전 검토 필수
