# t1.5 네트워크 전송 시간 측정 + 타임스탬프 기준점 정리

## 문제
스트리밍 STT에서 `t1_asr_final`이 클라이언트 시계, `t2_llm_final`이 서버 시계 → LLM 측정값에 시계 차이가 포함됨 (500ms vs 1500ms 차이의 원인).

## 목표
새 측정점 `t1_5_llm_start` 추가 + 기준 시계 통일.

### 새 타임스탬프 아키텍처

```
t0_user_end      [클라이언트] 정지 버튼/VAD
t1_asr_final     [서버]       STT 완료 (동기: STT 직후 / 스트리밍: gRPC is_final 수신)
t1_5_llm_start   [서버]       LLM POST 도착 = LLM 처리 가능 시점
t2_llm_final     [서버]       LLM 완료
t2_5_tts_ready   [서버]       TTS 완료
t3_audio_play    [클라이언트] 오디오 재생 시작
```

### 파생 지표

| 지표 | 공식 | 시계 | 의미 |
|---|---|---|---|
| STT | `t1 - t0` | 혼합(불가피) | STT 처리 시간 |
| **Network Transit** | `t1.5 - t1` | **서버-서버** ✅ | STT 완료 → LLM 시작까지 전송 시간 |
| **LLM** | `t2 - t1.5` | **서버-서버** ✅ | 순수 LLM 처리 시간 |
| TTS | `t2.5 - t2` | 서버-서버 ✅ | 순수 TTS (변경 없음) |
| Client Load | `t3 - t2.5` | 혼합(불가피) | 오디오 전송+로딩 |
| E2E | `t3 - t0` | 클라이언트-클라이언트 ✅ | 총 체감 시간 |

> [!NOTE]
> TTS는 이미 서버-서버 측정이므로 추가 변경 불필요.
